    気づき・課題

    途中経過メモ（2026-11-13 時点・単元進行中）

    第1〜3時（座学）

    • 大きな問題はなかった。

    第4時以降（PRIMM 演習）の授業の流れ

    起きたこと

    • 第4時「選択構造の基礎」は、コードを説明して実行結果を予想（Predict）→ 実行（Run）→ 調査（Investigate：初めて出てきた「条件式」の動きを調べる）→ 改変（Modify）の流れで進めた。
    • 1コマ（50分）では調査に十分な時間を取れなかった。
    • 一部の生徒は、予想・実行の段階で理解が追いついていなかった（ポカンとしていた）。
    • 次の授業からは、予想の前にコードを1行ずつ説明し、そのうえで予想 → 実行に進めた。生徒は理解できている様子だった。

    考察

    • 初めて出てくる概念を生徒自身に調べさせるのは、プログラミング初学者が1コマの中で取り組むには負担が大きい。
    • 概念は先に教師が説明し、演習の時間は「読む・動かす・直す・書く」に使うほうが合っている。

    改善案

    • 授業の流れを「初出概念の説明 → 予想 → 実行 → 改変 → 作成」に変える（調査の段階はなくす）。
      • 調査で扱うはずだった「各行が何をしているか」の理解は、冒頭の概念説明と、予想の前に1行ずつ行う説明で補う。
      • 現在の計画では、作成（Make）は第10・11時だけで行う。第4〜9時にも作成を入れるなら、短時間で終わる小さな課題にする必要がある。

    トレースについて（記録のみ・扱いは未定）

    • 生徒は、コードをトレース（変数の値の変化を順に追うこと）した経験がほとんどないようだ。
    • 予想の課題を「トレースしないと答えられない形」にすれば、コードを読む力を伸ばせる可能性がある。
    • ただし、トレースをどう取り入れるか（トレース表の様式、どの回から始めるかなど）はまだ決めていない。
    • 回によっては、トレースより別のこと（例：境界値のときの出力、どの分岐に進むか）を予想させたほうがよい内容もある。そのため、すべての回に一律で取り入れることはしない。

    Modify 課題の変更（反応がよかったもの・次年度に引き継ぐ）

    授業の中で計画から変えて出題し、生徒の反応がよかった Modify 課題を記録する。次年度は授業ファイルの Modify 課題をこの内容に差し替えることを検討する。

    回 計画時の課題 実際に出した課題 効果
    第5時 選択構造の複雑化 段階の閾値を変える／判定の順序をわざと入れ替えてバグを観察し、直す 90以上→5、70以上→4、50以上→3、30以上→2、それ以外→1 の5段階評価に書き換える elif の使い方の理解が深まった
    第6.5時 while文 「合計が目標値を超えるまで加算し、何回で超えたか求める」／「番兵 -1 が来るまで入力を合計する」に書き換える ①1〜100の合計を求める ②3〜100の3の倍数の合計を求める while 文で大事な「初期化・継続条件・更新」の理解が深まった
    第7時 反復と選択の複合 条件を「80点以上」に変える／人数ではなく合計点に変える／平均を出す（各課題が独立している） ①条件を「50点以上」（元のコードは60点以上）に変えて人数を数える ②50点以上の点数の合計を求める ①の結果を②でそのまま使えるため、流れがスムーズになった
