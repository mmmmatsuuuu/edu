    情報システム 評価まとめ

    実施期間

    年　月　日 〜 2026年10月6日（第1〜7時の座学まで。第8〜16時の演習は未実施）

    前提

    • 対象は3年11名。選択科目のため、全員を1クラスとみなして分析する。設問の回答数は9〜11名で、正答率は1人で約9〜11%動く（例：91%＝10/11人、89%＝8/9人、36%＝4/11人）。そのため、80%台後半以上の設問の差は1〜2名の誤答であり、設問の難しさの差とは言えない。70%台以下で差が大きい設問（並び替え・コードの読み取りなど）を中心に読む。
    • 組別の正答率は人数が1〜4名のため、0%や100%は内容の弱点ではなく特定の個人の可能性が高い。組別の数値は個別フォローの手がかりとしてのみ使う。
    • 本まとめは第1〜7時（座学）の小テスト・生徒メモに基づく。第8〜16時（演習）の記録シート（設計・実装・検証）・実装物・運用記録・振り返りレポート、単元テスト（第16時）は本データに含まれない。評価基準のうち「生成AIを活用して担当パーツを構築する」「設計意図やトレードオフを言語化する」「文化祭運用への主体的な取り組み」は演習で見る内容のため、評価は暫定。
    • 小テストは各回の座学の後に実施したものとして扱い、補習・演習の前後による影響は考えない。
    • 生徒メモは28件（各回4件）のサンプル。傾向の参考にとどめる。
    • 本単元は中間まとめで、次単元（04_データサイエンス）の計画作成に向けたフィードバックを目的とする。

    観点別評価結果

    観点 評価 所見
    知識・技能 4 高定着：情報システムの4つの働き（2301 Q1〜Q4・Q7・Q10：100%）、クライアント/サーバとGET/POSTの対応（2302 Q8：100%）、静的/動的サイトの違い（2304 Q2：100%）、URLパラメータの役割（Q5：100%）、if・forの役割と配列/オブジェクト（2305 Q2・Q3・Q8：100%）、APIの概念（2306 Q1・Q3：100%）、AIコードの検証の姿勢（2306 Q4・Q5・Q7：100%）、要件定義・状態遷移・モジュールの意味（2307 Q1・Q3・Q4：100%）。選択式の概念問題の多くが80%以上。
    やや低め：ハードウェアの判別（2301 Q5：67%）、レコードの呼称（2303 Q2：67%）、主キー（Q3：78%）、正規化の目的（Q5：78%）、JSの役割（2304 Q4：70%）、関数の説明（2305 Q7：73%）、PythonとJSの違い（Q6：73%）。
    コードの読み取りに課題：繰り返しで合計を追う設問が36%（2305 Q5、誤答は「3」に7名が集中）、エラーの原因（const の再代入）が55%（Q12、36%は「if文がないため」と誤答）、天気APIを使う場面の設問（Q13）が60%（誤答は「大阪」に3名）。
    手順の並び替えは5/6回で最低水準（下記の思考・判断を参照）。
    評価基準の前半（構成要素・ネットワーク・QRの説明）は多くが到達。後半（生成AIで担当パーツを構築し、動作を確認・説明する）は演習の実装記録・実装物が本データにないため確認できず、暫定とした。
    思考・判断・表現 3 評価基準の評価方法（設計記録・検証記録・振り返りレポート）は本データに含まれない。小テストから見える範囲では、用語を使った説明は良好（2302 Q9：リクエスト/レスポンスを使った説明は3件中3件が要点を押さえている、2303 Q10：主キー・外部キーの違いは3件中3件が正確、2304 Q9：静的/動的の違いは3件中3件が要点を押さえている、2306 Q9：APIを窓口で説明は3件中3件が正確）。
    一方、理由・根拠・具体例まで書ききれていない回答が目立つ：情報システムの定義（2301 Q9：3件とも「入力・処理・蓄積・出力」の流れの説明にとどまり、ハードウェア・ソフトウェア・データ・人の構成要素に触れていない）、ネットワークの利点（2302 Q10：「速さが違う、手間が省ける」など、スタンドアロンとの違いを書けていない回答あり）、生成AIの活用（2306 Q10：「作業が早くなる。必要なことは適切な指示。」と、検証に触れない回答あり）、要件定義の理由（2307 Q9：「必要な処理を先に固められるから」など短く、手戻りという理由の部分が薄い）、擬似コード（Q10：「効率が良くなる」）。
    手順・流れを順序づける設問が低い：URLを入力してからページが表示されるまで（2302 Q6：50%）、正規化の流れ（2303 Q6：67%）、生成AIでコードを動かすまでの流れ（2306 Q6：50%）、システム設計の進め方（2307 Q5：50%）。前単元（01_情報社会）の弱点と同じ傾向が続いている。
    主体的に学習に取り組む態度 3 評価基準の評価方法（演習活動状況・運用記録）は本データに含まれない。メモからは、視聴内容を表や例で整理する丁寧な記述（POSをレジに、交通系ICを改札に置き換えるなど）や、自分の言葉での気づき（2301「データがなければ処理が意味ない」、2306「作成AIはもっともらしく間違える」）が見られ、授業に前向きに取り組んでいる様子はうかがえる。ただし、責任者としての品質保証やチームでの取り組み、トラブル対応は演習・文化祭運用で見る内容で、確認できないため3を基本とした。

    評価は授業改善のため、単元計画の評価基準に照らして生徒の到達度を見る5段階の目安（5：ほぼ全員が到達／4：多くが到達（一部につまずき）／3：おおむね到達（主要部分に課題）／2：到達した生徒が少ない／1：ほとんど到達していない）。学校の評価・評定とは別で、一致させる必要はない。すべて暫定：知識・技能は第1〜7時の座学分のみに基づく。思考・判断・表現と主体的な態度は、演習の記録シート・実装物・運用記録・振り返りレポート・単元テストが本データに含まれないため、3を基本とした。演習の資料が得られたら見直す。

    気づき・課題

    ※実施範囲・暫定：第1〜7時（座学）の小テスト・メモに基づく考察。演習（第8〜15時）と単元テスト（第16時）は未反映。

    目標の達成度

    • 情報システムの構成要素・ネットワーク・QRの仕組みの理解：ほとんどの生徒が到達。4つの働き（100%）、クライアント/サーバ・GET/POST（90〜100%）、静的/動的サイト・URLパラメータ（100%）など、スタンプラリーの文脈に結びつけた概念は定着している。
    • データ管理（テーブル・主キー・外部キー）：記述（主キーと外部キーの違い）は3件中3件が正確。一方、選択式ではレコードの呼称（67%）・主キー（78%）・正規化の目的（78%）にばらつきがあり、用語は書けても、図表の中で当てはめる場面で1〜3名がつまずく。
    • プログラミング（読む力）：if・for・配列/オブジェクトは100%だが、コードを実際に追って値を求める設問（36%）やエラーの原因を読み解く設問（55%）が低い。単元の目標「AIが書いたコードを検証し、説明できる」の土台にあたる部分で、演習前に補う必要がある。第5時の目標は「なんとなく読める」で、コードの説明（Q10：3件中3件が内容を正しく説明）はできているが、値を追跡する精度は不足している。
    • 生成AIの活用と検証：「出力を鵜呑みにせず検証する」という姿勢を問う設問は100%（Q4・Q5・Q7）。一方、基本の流れの並び替えは50%、記述で検証に触れない回答もあり、姿勢は理解しているが、手順として整理できていない。演習③④の中心になる内容のため、手順の定着が課題。
    • システム設計の進め方：要件定義・状態遷移・モジュールは100%。進め方の並び替えは50%、モジュール分割の「適切でない利点」を選ぶ設問は50%。
    • 担当パーツの構築・設計意図の言語化・文化祭運用：演習が未実施のため判断できない。

    授業構成・時間配分

    • 第1〜7時は動画視聴（15〜20分）＋アプリと関連づける確認・深化（15〜22分）の構成で統一されている。概念系の設問が高定着であることから、座学の構成は機能している。
    • スタンプラリーの文脈に結びつけた説明は定着している：第2時のGET/POSTとスタンプ記録の対応（Q8：100%）、第4時のURLパラメータとブースID（Q5：100%）など、アプリに関連づけた回の設問が高い。
    • 第5時（プログラミングの基礎）は内容が多い：復習・PythonとJSの対比・変数・if・for・関数・配列・GASを18分の動画で扱い、PRIMMの活動が20分。コードの追跡（36%）・const（55%）・関数（73%）が低く、詰め込み気味でPRIMMのPredict→Run→Investigateを十分に回せていない可能性がある。PRIMMの時間確保が必要。
    • 第6時は体験演習の22分でAIによる生成→実行→検証を1周する構成だが、並び替え（50%）や記述で検証に触れない回答があり、1周では手順の定着まで届いていない。
    • 第7時の「システム設計の進め方」と「スケルトン読解」は18分＋20分で収まっている。ただし、進め方の並び替えが50%で、読解の活動の後に定着確認の時間は取れていない。
    • 小テストの設問数は2305が12問、2306が13問と、他の回（10問）より多い。

    ストロングポイント（得意）

    • 概念・用語の理解と、用語を使った説明：4つの働き、クライアント/サーバ、静的/動的、API、モジュールなどを正確に説明できる。記述（2302 Q9・2303 Q10・2304 Q9・2306 Q9）で、キーワードを押さえた説明が安定している。
    • 既習内容の接続：メモに「クライアント・サーバの関係そのもの」（2306）と書くなど、前の回の知識とつなげて理解している記述がある。
    • 生成AIの扱い方の姿勢：具体的な指示（プロンプト）、鵜呑みにしない、テスト入力で確かめる、といった作法を選択式でほぼ全員が理解している（100%）。
    • コードの大まかな内容を説明する力：2305 Q10（コードの説明）は3件とも内容を正しく説明している。
    • 前単元で見られた「概念・記述が得意」という強みが、今回も続いている。

    ウィークポイント（つまずき）

    • 手順・流れを順序づける設問（並び替え）：2301 Q4（100%）を除くと、2302 Q6（50%）、2303 Q6（67%）、2304 Q8（80%）、2306 Q6（50%）、2307 Q5（50%）と低め。前単元の弱点と同じで、図解・段階提示を取り入れた効果は限定的。特に2306 Q6（生成AIでコードを動かすまで）と2307 Q5（設計の進め方）は、演習で直接使う手順にあたる。
    • コードの追跡とエラーの読み取り：2305 Q5（36%）は誤答が「3」に7名集中しており、同じ誤解（ループの回数や途中の値の取り違えなど）が起きている可能性がある。ただし選択肢の中身が本データからは判別できないため、問題文を確認して原因を特定したい。Q12（55%）は、const で宣言した変数にループ内で値を代入するエラーの原因を、「if文がないため」（36%）と誤る回答が目立つ。let と const の違い（PythonになくてJSにある点）を読み落としている。
    • 関数の理解：関数の説明（2305 Q7：73%）が低め。担当パーツはすべて純粋関数であり、単元の中心概念のため重要。
    • 細部の用語の取り違え：ハードウェアの判別（2301 Q5：67%）、レコードとフィールド（2303 Q2：67%）、JSの役割（2304 Q4：70%）。メモにも「NTTP・DWS」（HTTP・DNS）、「要件定理」（要件定義）、「GAS＝JavaScriptとgoogle独自のAI」などの誤記・混同が見られる。
    • 否定形の設問：2307 Q8（「適切でないもの」を選ぶ：50%）。誤答は「分担できる」（30%）・「再利用できる」（20%）に分散しており、内容の弱点よりも「適切でない」を読み落とした可能性がある。
    • 理由・根拠まで書く記述：定義を構成要素まで説明する（2301 Q9）、利点を具体的に書く（2302 Q10）、理由を書く（2307 Q9）、擬似コードの役立ち方を書く（Q10）で、短い回答や要点のずれが見られる。単元の重点である「設計意図・トレードオフの言語化」の土台に課題がある。
    • 特定の個人のつまずき（個別フォローの手がかり）：1組（1名）は第3時（データの管理）で選択式の多くを誤答し、以降も散発的に誤答がある。6組（50%刻みから2名）は第2時以降、各回で1名分の誤答が続いている。4組は第5時（Q5：0%、Q12：25%）でコードの追跡に誤答が集中している。評価ではなく、演習でのつまずきを把握する手がかりとして扱う（人数が少ないため、断定はしない）。

    興味関心

    • 身近なシステムやスタンプラリーに結びつけた理解：POSシステム・交通系IC・ATMなど身近な例を挙げ、メモで整理している（2301）。URLやQRコードへの関心も見られ、「どこからアクセスしたかを計測・分析する」（2304 Q10）のように、データを活用する視点を書いた回答もある。これは次のデータサイエンス単元につながる。
    • 生成AIの活用：メモに「ハルシネーション」「サンドボックス」「テスト入力で動作を確認」と書いており、検証の流れへの関心がある。
    • ただし、メモは視聴内容の書き取りが中心で、自分の関心や疑問を書いた記述は少ない。関心の強さはメモからは読み取りにくい。演習の担当パーツ選び（希望アサイン）の結果で関心を確認したい。

    次単元・演習に向けた改善案と注意点

    演習（第8〜15時）に向けて

    1. 手順の並び替えの弱さを演習の進め方で補う：第10時の冒頭で「指示→実行→確認→修正」の流れ（2306 Q6：50%）を掲示し、各自の実装記録に4ステップのチェック欄を設ける。設計では、フローチャートや擬似コードを「順序カードを並べてから清書する」形で書かせる。
    2. コードを追う力を第10〜11時の前に補う：変数の値の変化を書くトレース表（ループの1回ごとの値を書く）を1回分入れる。第10時でAIが出したコードを読むときは、「Predict（予想）を先に書いてから実行する」を徹底する。let と const の違いはエラー例（2305 Q12）として全体で確認する。
    3. 純粋関数の理解を演習の前に確認する：担当パーツは純粋関数だが、小テストに純粋関数を問う設問がない。第8時（パーツ決め）で、「入力→出力だけで、スプレッドシートに直接書かない」ことを小さな例（例：スタンプ数→ガチャ可否）で確認する。
    4. 記述に「理由」を書く型を渡す：設計記録は「仕様は〇〇にした。理由は〇〇。迷った選択肢は〇〇」の穴埋め型にする。第9時でよい記述例（匿名）を1〜2件共有する。第1時Q9のような定義も、構成要素を使って書く練習が必要。
    5. 責任者・パーツの割り当てで個別の状況に配慮する：コードの追跡（2305 Q5・Q12）でつまずきが見られる生徒が、実装責任者（コード生成・修正）を1人で担わないよう、ペアにする。難易度「中〜高」の重複/不正チェック関数は、コードを読む力のある生徒と組ませる。
    6. 個別フォロー：上記の1組・6組・4組のつまずきを手がかりに、演習の序盤（第8〜9時）で声をかけ、実態を把握する。

    次単元（04_データサイエンス）に向けて

    • 単元冒頭でレコード・フィールド・主キーを短く復習する：選択式でレコード（67%）・主キー（78%）にばらつきがあり、運用データ（記録テーブル）を扱う導入で必要になる。
    • 文化祭の運用データの列を事前に確認する：データの管理の理解は記述でおおむね良好なので、「記録テーブルのどの列が何を表すか」を最初に整理すれば、分析に入りやすい。
    • 「データを活用する視点」を生かす：2304 Q10で「アクセスの計測・分析」に触れた生徒がいる。運用データ集計関数（第8時のパーツ）で決めた集計軸を、データサイエンス単元の問いにつなげる。
    • 手順（データの収集→整理→分析→可視化）の並び替えが弱い可能性がある：本単元の並び替えの傾向から、プロセス図を提示して順序を整理する時間を設ける。

    扱った内容の妥当性（次年度に向けて）

    • 全体評価：座学7回の構成（情報システム→ネットワーク→データ→QR・Webアプリ→プログラミング→API・生成AI→全体設計）は、スタンプラリーの構築に向けた段階的な順序として妥当。概念系は高定着で、アプリに関連づける展開が機能している。
    • 修正した方がよい部分：第5時（プログラミングの基礎）が過密。復習・PythonとJSの対比・関数・配列・GASを1コマに詰めており、コードの追跡（36%）・const（55%）・関数（73%）に課題が残る。値の追跡（トレース表）とエラーの読み取りの時間を確保し、動画の内容を絞る。第6時は、AIによる生成→検証を1周するだけで終わらず、手順を整理する時間を取る。
